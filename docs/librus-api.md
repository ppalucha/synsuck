# Librus — observed web flow (Oct 2026)

Reverse-engineered from browser traffic of a parent ("Librus Rodzina" → Synergia) login.
Unofficial; Librus may change any of this without notice.

All requests: normal browser `User-Agent`; session is purely cookie-based
(one cookie jar per account, shared across `api.`, `synergia.`, `wiadomosci.` and
`sandbox.librus.pl`). Follow redirects manually or let OkHttp follow them — cookies
are set along the redirect chain.

## 1. Login (OAuth, `client_id=46`)

| # | Request | Result |
|---|---|---|
| 0 | `GET https://synergia.librus.pl/loguj/portalRodzina` | 302 → `api.librus.pl/OAuth/Authorization?client_id=46&response_type=code&scope=mydata&state=…`; sets `oauth_state` + Synergia session cookies. **Required** — starting directly at step 1 logs in to OAuth but Synergia rejects the callback (no matching state). |
| 1 | follow → `GET https://api.librus.pl/OAuth/Authorization?…` | 302 → `/OAuth/Authorization?client_id=46` (login form, sets cookies) |
| 2 | `GET https://api.librus.pl/OAuth/Authorization?client_id=46` | 200 HTML |
| 3 | `POST https://api.librus.pl/OAuth/Captcha` form: `username`, `is_needed` | `{"is_needed": false, "reCaptchaCode": ""}` |
| 4 | `POST https://api.librus.pl/OAuth/Authorization?client_id=46` form: `action=login`, `login`, `pass` | `{"status": "ok", "goTo": "/OAuth/Authorization/2FA?client_id=46"}` |
| 5 | `GET https://api.librus.pl` + `goTo` | 302 → `/OAuth/Authorization/PerformLogin` → 302 `/OAuth/Authorization/Grant` → 302 `https://synergia.librus.pl/loguj/portalRodzina?code=…&state=…` |
| 6 | `GET` that Synergia URL | 200 — Synergia session cookie established |

Notes:
- Step 4 is sent as XHR: `Content-Type: application/x-www-form-urlencoded; charset=UTF-8`,
  `X-Requested-With: XMLHttpRequest`, plus a header `X-Baner: <opaque string>` generated by
  obfuscated JS. **Not required** — confirmed login works without it (Oct 2026).
- If step 3 returns `is_needed: true`, a reCAPTCHA is required → cannot log in headlessly;
  surface as an account error ("log in once via browser").
- Failed login: step 4 returns a non-`ok` status (exact shape TBD — capture a failed login
  to confirm). Treat as `AUTH_FAILED`.
- The browser starts from `portal.librus.pl/rodzina/synergia/loguj` (iframe); the app can
  skip the portal and start at step 0.

## 2. Messages module handoff

| Request | Result |
|---|---|
| `GET https://synergia.librus.pl/wiadomosci3` | 302 → `https://wiadomosci.librus.pl/pobierzNN/MultiDomainLogon/token/<one-time>/login/<b64>/target/<b64>/from/<b64>` (`NN` varies: 15, 17, … — just follow the redirect) |
| follow | 302 → `/nowy` — `wiadomosci.librus.pl` session cookie established |

After this, the JSON API under `https://wiadomosci.librus.pl/api/` is usable and the
session can be reused for further calls. Session expiry → expect 401/redirect; re-run login + handoff.

## 3. Messages API (`https://wiadomosci.librus.pl/api`)

Plain `GET`s with cookies; the web app also sends `Content-Type: application/json`.

### `GET /me`
`firstName`, `lastName`, `groupName`, `accountId` (int), `accessToAttachments` (bool), …
→ use to verify login and to pre-fill the account label.

### `GET /inbox/unreadMessagesCount`
```json
{"data": {"inbox": 0, "notes": 0, "alerts": 0, "trash": 0, "archiveInbox": 4, ...}}
```
Note: unread counts exist for both `inbox` and `archiveInbox` — archived messages
(previous school year?) can also be unread.

### `GET /inbox/messages?page=1&limit=10`  — list, **does not mark as read**
```json
{
  "data": [{
    "messageId": "1028812",           // string
    "senderFirstName": "…", "senderLastName": "…", "senderName": "…",
    "topic": "…",
    "content": "…",                    // plain-text preview, truncated
    "sendDate": "2026-10-06T21:49:51", // local time (Europe/Warsaw), no offset
    "readDate": "2026-10-06T21:50:14", // null = unread (confirmed)
    "tags": [], "category": null,
    "isAnyFileAttached": false
  }],
  "total": 17
}
```
Sorted newest first. Background sync: fetch page 1 and continue only while the page
contains message ids not yet known locally.

### `GET /inbox/messages/{messageId}` — detail, **marks as read**
Key fields:
- `topic`, `senderName`, `senderGroup`, `sendDate`, `readDate`
- `Message` — **base64** of an XML document:
  `<Message><Content><![CDATA[ plain text, \n line breaks ]]></Content><Actions>…</Actions></Message>`
  (no HTML observed so far; render as text with linkified URLs, but tolerate HTML)
- `attachments`: `[{"id": "5496406", "filename": "…"}]`
- `attachementInfo` (sic): human-readable note, sometimes plain text, sometimes base64
- `noReply`, `isMessageWithdrawn`, `archive`

### `GET /attachments/{attachmentId}/messages/{messageId}`
```json
{"data": {"status": "ok", "downloadLink": "https://sandbox.librus.pl/GetFile/<token>"}}
```
Then, with the same cookie jar:
1. `GET downloadLink` → ~6 KB `text/html` info page ("Pobieranie plików", wait ≥5 s).
2. `GET downloadLink + "/get"` with `Referer: downloadLink` → the file
   (`Content-Disposition: attachment; filename…`, real content type). In the browser a script
   on the info page triggers this; the HTML served to non-browser clients has no script, so
   the client requests `/get` itself, retrying while the response is still `text/html`.

### Archive (from the web app's JS bundle)
Same shapes as the inbox:
- list: `GET /archive/inbox/messages?page=&limit=`
- detail: `GET /archive/inbox/messages/{messageId}` (marks as read)
- attachment link: `GET /archive/attachments/{attachmentId}/messages/{messageId}`

The web app simply does `window.open(downloadLink)` for attachments.

### Other endpoints seen (not needed for v1)
`/receivers/student-subjects`, `/tags`, `/inbox/messages/senders`, `/auth/logout`.
